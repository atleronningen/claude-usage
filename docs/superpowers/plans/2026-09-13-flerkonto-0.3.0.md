# Flerkonto-støtte i Claude Usage

## Kontekst

Appen er i dag bygget for nøyaktig én Claude-konto. `config.load_credentials()`
returnerer en flat `tuple[str, str]`, `fetch_usage(cookie, api_url)` kalles én
gang per minutt, og menyen har ett fast sett elementer (`session_meter_item`,
`weekly_meter_item`, …) opprettet én gang i `__init__`. Ordet «konto» finnes
ikke i kildekoden.

Brukeren har to Claude-kontoer: en privat Pro-konto og en Team-konto gjennom
jobben. Det er to separate claude.ai-innlogginger, altså to ulike
sesjonscookies og to ulike org-ID-er. I dag må man redigere `.env` manuelt for
å bytte mellom dem, og man ser aldri forbruket på begge samtidig.

Målet er at appen håndterer N kontoer: alle hentes hvert minutt, alle vises i
dropdown-menyen med fulle målere, og menylinjetittelen viser den kontoen du har
valgt som aktiv.

## Beslutninger

Avklart med brukeren under brainstorming:

1. **Tittel** viser kun aktiv konto, i dagens format `43 · 76`. Uendret bredde.
2. **Dropdown** viser alle kontoer med fulle målere og nullstillingslinjer.
   Aktiv konto er markert, og et klikk på en annen konto bytter aktiv konto.
3. **Henting**: alle kontoer hentes hvert minutt, ett HTTP-kall per konto.
4. **Kontonavn** er plantypen: «Pro», «Max», «Team Plan».
5. **Konfigurasjon**: nummererte nøkler i `.env`. Gamle unummererte nøkler
   fortsetter å virke som konto 1, så brukerens eksisterende `.env` ikke må røres.
6. **Tråder**: hentingen flyttes ut av hovedtråden og kjøres parallelt, så
   menylinjen aldri fryser og totaltiden er ~10 s uansett antall kontoer.

## Fase 0 – Verifiser Team-endepunktet først

Dette er et ekte usikkerhetsmoment som kan endre resten av designet. Team-planer
har seter og delte grenser, og `/api/organizations/<org-id>/usage` kan derfor
returnere en annen form enn `five_hour`/`seven_day` – eller bli avvist av
org-policy.

1. Brukeren henter cookie og Request URL for jobbkontoen fra DevTools, samme
   oppskrift som i README punkt 1–5. De to kontoene må hentes fra hver sin
   nettleserprofil, siden claude.ai bare holder én innlogging per profil.
2. Kall endepunktet én gang og dump rå-JSON:

   ```bash
   venv/bin/python -c "
   from curl_cffi import requests
   r = requests.get('<TEAM-URL>', headers={'Cookie': '<TEAM-COOKIE>'}, impersonate='chrome', timeout=10)
   print(r.status_code); print(r.text[:2000])
   "
   ```

3. Vurder resultatet:
   - Samme form (`five_hour.utilization`, `seven_day.utilization`, `resets_at`)
     → resten av planen gjelder uendret.
   - Annen form → stopp og brainstorm datamodellen på nytt før fase 2.
   - 401/403/404 → Team-kontoen eksponerer ikke dette. Da er flerkonto-støtten
     fortsatt nyttig (Pro + Max, eller to private kontoer), men uten jobbkontoen.

Ingen kode committes i denne fasen.

## Fase 1 – Datamodell og config

### Ny modul: `claude_usage/accounts.py`

Holder kontobegrepet samlet, utenfor både `config.py` (som handler om å lese
filer) og `usage_client.py` (som forblir uendret og statsløs).

```python
@dataclass(frozen=True)
class Account:
    key: str          # stabil identitet, f.eks. "1" – brukes til persistering
    label: str        # visningsnavn, f.eks. "Pro" / "Team Plan"
    cookie: str
    api_url: str


@dataclass(frozen=True)
class AccountUsage:
    account: Account
    usage: UsageData | None      # None ved feil
    error: str | None            # feilmelding, None ved suksess
    actionable: bool             # om feilen kan fikses ved å oppdatere .env
    updated_at: datetime | None  # når usage sist ble hentet med hell
```

`AccountUsage` er den eneste typen `main.py` renderer fra. Den generaliserer
dagens `_last_usage` + `_last_updated_at` til per konto, og bærer «stale
tall»-tilstanden: `usage` satt og `error` satt samtidig betyr «gamle tall, ny
feil», som er nøyaktig dagens `_render_data_items_compact`-modus.

### `config.py`

Behold `env_file_path()`, `CONFIG_DIR` og `CredentialsMissingError` uendret.
Legg til:

```python
def load_accounts() -> list[Account]
```

Parseregler, i rekkefølge:

1. Les `dotenv_values(env_file_path())` på nytt ved hvert kall, som i dag, slik
   at `.env`-redigering plukkes opp uten restart. Shell-env (`os.environ`) slår
   filverdien for hver enkelt nøkkel – samme presedens som `load_credentials()`.
2. Skann `CLAUDE_USAGE_ACCOUNT_<N>_COOKIE` / `_API_URL` / `_LABEL` for N = 1..20.
   Hull i nummereringen hoppes over, ikke avbrytes – `ACCOUNT_1` og `ACCOUNT_3`
   uten `ACCOUNT_2` skal gi to kontoer. En konto krever både cookie og api_url;
   mangler én av dem, hoppes oppføringen over. Mangler `_LABEL`, brukes
   `f"Konto {N}"`. `key` settes til `str(N)`.
3. Hvis ingen nummererte kontoer ble funnet, fall tilbake til de unummererte
   `CLAUDE_USAGE_COOKIE` / `CLAUDE_USAGE_API_URL` som én konto med
   `key="legacy"` og `label="Konto 1"`.
4. Finnes både nummererte og unummererte nøkler, vinner de nummererte og de
   unummererte ignoreres. Det holder migreringen forutsigbar.
5. Er lista tom, kast `CredentialsMissingError("Mangler cookie/API-URL i .env")`
   – samme melding som i dag, så feiltilstanden i UI-et er uendret.

`load_credentials()` **fjernes**. Den har ingen andre kallere enn `main.py`, og
å beholde den som wrapper ville gitt to sannheter om hva «konto» betyr. Testene
for den erstattes av tilsvarende tester for `load_accounts()`.

### Aktiv konto

Nytt i `config.py`:

```python
STATE_FILE = CONFIG_DIR / "state.json"

def load_active_account_key() -> str | None
def save_active_account_key(key: str) -> None   # oppretter CONFIG_DIR ved behov
```

`CONFIG_DIR` (`~/.claude-usage`) er allerede definert og slettes allerede av
`_uninstall`, så avinstallasjonen trenger ingen endring.

Oppløsning av aktiv konto gjøres i `accounts.py`:

```python
def resolve_active(accounts: list[Account], stored_key: str | None) -> Account
```

Finnes `stored_key` blant kontoene, brukes den. Ellers første konto i lista.
Det dekker både første oppstart og tilfellet der kontoen er fjernet fra `.env`.
Filen skrives kun når brukeren aktivt bytter konto, aldri ved oppstart – da
unngår vi at en midlertidig feil i `.env` overskriver et gyldig valg.

Lese- og skrivefeil mot `state.json` (korrupt JSON, manglende skrivetilgang)
svelges og logges ikke – valget er en bekvemmelighet, ikke data verdt å krasje på.

## Fase 2 – Parallell henting i bakgrunnstråd

### Hentefunksjon

I `accounts.py`, uten noen som helst kjennskap til rumps:

```python
def fetch_all(accounts: list[Account], previous: dict[str, AccountUsage]) -> list[AccountUsage]
```

Kjører `fetch_usage` for alle kontoer parallelt med
`concurrent.futures.ThreadPoolExecutor(max_workers=len(accounts))`. Per konto
mappes `UsageAuthError` → `"Cookien utløpt – oppdater"` (actionable),
`UsageFetchError` → `str(exc)` (actionable), øvrige unntak →
`f"Uventet feil: {exc}"` (ikke actionable) – nøyaktig samme meldinger og
actionable-klassifisering som dagens `refresh`. Ved feil arves `usage` og
`updated_at` fra `previous[account.key]` hvis den finnes, slik at gamle tall
overlever. Funksjonen kaster aldri, og rører ingen UI-tilstand – derfor er den
trygg å kalle fra en hvilken som helst tråd og lett å teste isolert.

`usage_client.py` endres ikke i det hele tatt.

### Trådmønster i `main.py`

`rumps.Timer.start()` registrerer på `NSRunLoop.currentRunLoop()`, som er
hovedtrådens run-loop når timeren opprettes i `__init__`. Callbacken fyrer
derfor alltid på hovedtråden – det er nettopp derfor hentingen fryser
menylinjen i dag. Resultatet fra en bakgrunnstråd må marshalles tilbake.

Mønsteret, som holder all rumps-berøring på hovedtråden uten PyObjC-triksing:

```python
self._result_queue: queue.Queue[list[AccountUsage]] = queue.Queue()
self._fetch_in_flight = False

self.fetch_timer = rumps.Timer(self._start_fetch, REFRESH_INTERVAL_SECONDS)   # 60 s
self.drain_timer = rumps.Timer(self._drain, DRAIN_INTERVAL_SECONDS)           # 1 s
```

- `_start_fetch` (hovedtråd): returnerer umiddelbart hvis `_fetch_in_flight`.
  Ellers settes flagget og en `threading.Thread(daemon=True)` startes som kaller
  `fetch_all(...)` og legger resultatet på køen.
- `_drain` (hovedtråd): `queue.get_nowait()` i en try/`queue.Empty`, og ved treff
  `self._apply(results)` + nullstill flagget. Alle rumps-kall skjer her.
- `_apply(results)` (hovedtråd): all rendering – tittel, menyelementer, footer.

Kontrakten blir: **alt som rører `rumps` ligger i `_apply` og metodene den
kaller. Ingenting annet.**

### Testbarhet – kravet som styrer designet

De 14 testene i `tests/test_main.py` instansierer `ClaudeUsageApp()` og leser
`app.title` rett etterpå, fordi `__init__` kaller `refresh(None)` synkront.
Den egenskapen må bevares, ellers må alle skrives om.

Løsningen: behold en synkron `refresh(_sender)` som gjør
`self._apply(fetch_all(load_accounts(), self._last_by_key))` i kallerens tråd.
`__init__` kaller den én gang som i dag – førstehentingen ved oppstart er
fortsatt synkron, men skjer før menylinjen er i bruk. Deretter overtar
`fetch_timer` + `drain_timer` det periodiske arbeidet. Både den synkrone og den
asynkrone veien går gjennom nøyaktig samme `fetch_all` og `_apply`, så det
finnes ingen testet kodesti som produksjon ikke bruker.

Tester som vil verifisere trådveien kaller `_start_fetch(None)`, `join()`-er
tråden via en eksponert `self._fetch_thread`, og kaller så `_drain(None)`.

## Fase 3 – Dynamisk meny

### Fallgruve som styrer implementasjonen

I rumps 0.4.0 nøkles menyelementer på **tittelen** sin: `Menu.add()` →
`_process_new_menuitem(self._choose_key, value)` setter `key = value.title`, og
`Menu.__setitem__` starter med `if key not in self`. **To elementer med samme
tittel blir stille droppet.** Dagens kode unngår dette ved at hvert element får
en unik plassholdertittel ved konstruksjon («Sesjon-måler», «Uke-måler») og ekte
tittel settes etterpå.

Samme disiplin må gjelde per konto: elementene konstrueres med unike
plassholdertitler utledet av `account.key`, f.eks. `f"{key}-sesjon-måler"`, og
får ekte tittel i `_apply`. Ellers vil to kontoer med identisk forbruk
(`Sesjon  ▰▱▱▱▱▱▱▱▱▱ 8%` i begge) kollidere og den ene forsvinne fra menyen.

### Rebygging

`self.menu = [...]` kaller `Menu.update()`, som kun **appender** og ignorerer
eksisterende nøkler. En rebygging krever derfor `self.menu.clear()` først.
`clear()` kaller `removeAllItems()` på den samme `NSMenu`-instansen som
statuselementet peker på (satt én gang i `run()` via
`nsstatusitem.setMenu_(mainmenu._menu)`), så rebygging på en kjørende app er
trygg.

Siden `.env` leses på nytt hvert minutt, kan kontosettet endre seg mens appen
kjører. Mekanismen:

```python
def _ensure_menu_for(self, accounts: list[Account]) -> None
```

Sammenlign `tuple((a.key, a.label) for a in accounts)` med et lagret
`self._menu_signature`. Er de like, gjør ingenting – normaltilfellet hvert
minutt. Er de ulike, bygg `self._account_items: dict[str, AccountMenuItems]` på
nytt, kall `self.menu.clear()` og tilordne `self.menu = [...]` med den nye
strukturen, og oppdater signaturen.

`AccountMenuItems` er en liten dataklasse som holder de fem elementene per
konto: `header`, `session_meter`, `session_reset`, `weekly_meter`,
`weekly_reset`. Feilmeldingslinjen per konto gjenbruker `header`-elementet.

### Menystruktur

Flere kontoer:

```
Pro                        ← header, state=1 (hake), klikkbar
  Sesjon  ▰▰▰▰▱▱▱▱▱▱ 43%
  Nullstilles 14:30 (om 2 t 15 min)
  Uke     ▰▰▰▰▰▰▰▰▱▱ 76%
  Nullstilles tir 09:00 (om 3 d)
──────────
Team Plan                  ← header, state=0, klikkbar
  Sesjon  ▰▱▱▱▱▱▱▱▱▱ 12%
  ...
──────────
Avinstaller
Avslutt
──────────
Oppdatert 14:30 · App v0.3.0
```

Aktiv konto markeres med rumps' `MenuItem.state = 1` (ekte macOS-hake) på
header-elementet, ikke med et tekstprefiks. Header-elementene har callback
`self._select_account` og er dermed ikke utgrånet; måler- og
nullstillingslinjene beholder dagens `_noop`/`None`-skille for fullvekt vs.
dempet tekst.

Ved **nøyaktig én konto** droppes header-linjen og hakene helt, og menyen ser ut
nøyaktig som i dag. Det holder den vanlige enkeltkonto-bruken uendret og er
grunnen til at `format_title` kan beholde signaturen sin.

### Tittel og feiltilstander

`format_title(session, weekly, threshold)` beholdes uendret – den får tallene
fra aktiv konto.

- Aktiv konto OK → `43 · 76`, uansett om andre kontoer feiler.
- Aktiv konto feiler, men har gamle tall → `⚠️`, og aktiv kontos linjer vises
  dempet uten nullstillingslinjer (dagens compact-modus).
- Aktiv konto feiler uten gamle tall → `⚠️` og kontoens linjer skjules; kun
  feilmeldingen under headeren.
- En ikke-aktiv konto som feiler påvirker ikke tittelen, men viser feilmeldingen
  sin under sin egen header.

Dagens `error_item`/`help_item`/`top_separator` øverst i menyen beholdes for
feil som gjelder hele appen (`CredentialsMissingError` – ingen kontoer i det
hele tatt). Per-konto-feil vises derimot under den aktuelle kontoens header.

`_show_help` tar nå kontoen som feiler som argument og navngir de konkrete
nøklene i oppskriften (`CLAUDE_USAGE_ACCOUNT_2_COOKIE` / `_API_URL`), slik at
det er entydig hvilken cookie som må fornyes.

## Avvik fra planen under implementering

Tre punkter ble endret etter en designgjennomgang, før koden ble skrevet.

**`Account` bærer `.env`-nøkkelnavnene sine.** Planen antok at hjelpeteksten
kunne utlede nøkkelnavnet fra kontonummeret. Det er feil for et gammelt
oppsett, der cookien ligger under `CLAUDE_USAGE_COOKIE` og ikke
`CLAUDE_USAGE_ACCOUNT_1_COOKIE` — hjelpeteksten ville pekt på en nøkkel som
ikke finnes i brukerens fil. `Account` har derfor `cookie_env_key` og
`api_url_env_key`.

**Eksplisitte menynøkler i stedet for unike plassholdertitler.** Planen løste
rumps' tittelnøkling ved å gi hvert element en unik plassholdertittel. Det
dekker like målerverdier, men ikke to kontoer med samme etikett — headerne
ville fortsatt kollidert. Løsningen er `self.menu[f"konto:{key}:sesjon"] = item`,
som gjør nøkkelen uavhengig av tittelen.

**`AppHelper.callAfter` i stedet for drain-timer.** Planen marshallet resultatet
tilbake til hovedtråden med en `queue.Queue` og en ekstra timer som pollet hvert
sekund. rumps importerer allerede `PyObjCTools.AppHelper`, så `callAfter` gjør
samme jobb uten polling. Appen tar planleggingen inn som to sømmer
(`background`, `on_main`), slik at testene kjører alt synkront — produksjon og
test bruker dermed nøyaktig samme kodesti, uten `join()` eller event-loop.

Ett avvik oppsto under verifisering: siste kontos skillelinje ga to streker på
rad over «Avinstaller», siden handlingene har sitt eget skille. Skillelinjen
skjules nå for siste konto.

`state.json`-lagringen ble liggende i `config.py` framfor en egen modul, og
kontobegrepet i `accounts.py` framfor en egen `usage_service.py` — for en app på
denne størrelsen ga flere filer ingen gevinst.
